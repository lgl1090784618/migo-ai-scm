# MOSSDOOM 经营系统 — 部署与迁移手册

> 适用范围：从零部署、版本升级、跨服务器迁移。本文随代码仓库走，是部署的唯一权威操作文档。
> 密码/密钥一律不放本文档明文，只标注「在哪个文件读取、如何生成」；当前测试机的实际值请向管理员索取（见 §5 说明）。
> 新手日常操作（看日志/重启/备份）另见 `运维操作手册.md`；哪些组件免费/收费见 `组件许可证与费用清单.md`。

## 1. 系统概览

| 组件 | 技术 | 说明 |
| --- | --- | --- |
| 后端 | Java 21 / Spring Boot 3.5.16 | 单 JAR，内置 Flyway 迁移与 React 前端静态资源 |
| 前端 | React 19 / TypeScript / Vite | `npm run build` 产物打进后端 JAR，运行时不依赖 Node |
| 数据库 | PostgreSQL 17 | 双库：`moss_ingestion`（采集库）+ `moss_business`（业务库） |
| 对象存储 | SeaweedFS（S3 兼容） | 原文事件字节留存，桶 `moss-raw-test` |
| 网关 | Nginx | 对外只暴露 HTTPS 8443，反向代理 app:8080 与 /prometheus/ |
| 监控 | Prometheus + node-exporter | 基础设施与应用指标（actuator/prometheus） |
| 编排 | Docker Compose | 项目名 `mossdoom-test`，6 个服务 |

**处理链路（只读采集）**：令牌绑定 → 协议校验 + 原文写 S3（SHA256）→ 采集库写批次/事件/outbox/审计返 202 → worker 行锁租约领取 → 业务库写 inbox + 通用投影 → 隔离异常。无跨库分布式事务，最终一致性。

## 2. 服务器要求

- Linux（已在 Ubuntu 24.04 验证），≥4 核 8G 内存
- Docker Engine + `docker compose` 插件（server 29.x 验证过）
- 一个 sudo 用户（部署用），一个专用自动化密钥（SSH 免密）
- 磁盘：`/srv` 预留持久数据空间（Postgres/对象存储/备份）

## 3. 目录与文件布局

```
/opt/mossdoom/
  current -> releases/<active>        # 稳定入口符号链接
  releases/<YYYYMMDD>-<name>/         # 每次发布的完整快照（含 compose.yaml、脚本、.env）
    compose.yaml  bootstrap.sh  postgres-init.sh  nginx.conf  prometheus.yml  alerts.yml
    index.html  Dockerfile.prometheus  Dockerfile.seaweedfs  install-*.sh  backup.sh  smoke.py
    .env                              # APP_IMAGE/POSTGRES_IMAGE/... 锁镜像 digest，勿手改
    previous-release                  # 上一个版本的路径（回滚用）
  build/<YYYYMMDD>-<name>/            # docker build 上下文（app.jar + Dockerfile）
  artifacts/  attempts/  validation/  # 部署产物、历史尝试、验收记录

/srv/mossdoom/                        # 持久数据（独立于 releases，升级不丢）
  postgres/  objectstore/  prometheus/  backups/  metrics/

/etc/mossdoom/
  secrets/                            # 全部凭据（见 §4）
  tls/                                # server.key / server.crt（自签或可信证书）
```

## 4. 凭据清单（/etc/mossdoom/secrets/）

| 文件 | 用途 | 权限 |
| --- | --- | --- |
| `pg_admin` | PostgreSQL 超级用户 `moss_admin` 密码 | 644（compose 只读挂载） |
| `pg_ingestion` | 采集库角色 `moss_ingestion_app` 密码 | 644 |
| `pg_business` | 业务库角色 `moss_business_app` 密码 | 644 |
| `app_admin_password` | 应用管理员 `admin` 密码 | 644 |
| `app_viewer_password` | 应用只读用户 `viewer` 密码 | 644 |
| `monitor_password` / `monitor.htpasswd` | Prometheus 监控页 Basic Auth | 600 |
| `s3.json` / `s3-admin-client.json` / `s3-ingestion-client.json` | 对象存储身份 | 644 / 600 / 600 |
| `connector_key` | 平台凭据 AES-256-GCM 加密密钥（32 字节） | 644 |
| `connector-targets.json` | 出站目标白名单（3 个 test 主机 + endpoint_ids） | 644 |

生成：`bootstrap.sh` 首次运行时用 `secrets.token_urlsafe(36)` 自动生成 pg_*/monitor_*/s3，并生成自签名 TLS。已有环境请勿重跑生成逻辑，直接复用既有文件。

## 5. 数据库连接信息

- **Postgres 容器**：`mossdoom-test-postgres-1`，docker 内网 IP 随 compose 网络分配（当前 `172.18.0.4`），端口 `5432/tcp` —— **默认不映射到宿主机**，只对内网服务开放。
- **三个角色与库**：

| 角色 | 密码文件 | 可连库 | 用途 |
| --- | --- | --- | --- |
| `moss_admin` | `pg_admin` | 全部（postgres/moss_admin/moss_business/moss_ingestion） | 超级管理 |
| `moss_ingestion_app` | `pg_ingestion` | `moss_ingestion` | 采集库应用账号 |
| `moss_business_app` | `pg_business` | `moss_business` | 业务库应用账号 |

- **连接方式（任选）**：

  1. **服务器上直连**（推荐，最稳）：
     ```bash
     sudo docker exec -it mossdoom-test-postgres-1 psql -U moss_admin -d moss_ingestion
     ```
  2. **SSH 隧道 + 本机 GUI（DBeaver/Navicat）**：
     ```bash
     # 本地：动态取容器 IP 后建隧道
     ssh -L 15432:<容器IP>:5432 migo@192.168.10.154
     # DBeaver 连 localhost:15432，库名 moss_ingestion，用户 moss_admin
     ```
     注意容器 IP 在 compose 重启后可能变化，用 `sudo docker inspect mossdoom-test-postgres-1 --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}'` 现查。
  3. **临时端口映射**（不推荐，破坏「5432 仅内网」的默认安全边界）：在 compose.yaml postgres 段加 `ports: ['192.168.10.154:15432:5432']` 后 `docker compose up -d postgres`，用完删除。

> 实际密码值在对应 secrets 文件里，不在本文档明文。当前测试机已部署环境的真实值，管理员在服务器 `sudo cat /etc/mossdoom/secrets/<文件>` 即可读到。

## 6. 构建与发布

### 6.1 本机构建（Windows）

```bash
# 前端
cd frontend && npm ci && npm run build          # 产物 frontend/dist
# 后端（需 JDK21；离线 m2 仓库可选）
cd backend
export JAVA_HOME=G:\app\java\jdk21             # 本机 jdk21 路径
mvn -o package -DskipTests \
  -Dmaven.repo.local=<E盘m2仓库> \
  -Dmoss.build.directory=<E盘构建目录> \
  -Dmoss.frontend.directory=<frontend/dist 绝对路径>
# 产物：<构建目录>/mossdoom-platform-0.1.0.jar
```

关键约定：`mvn` 必须在 `backend/` 目录内执行（POM 在 backend/pom.xml）；前端静态资源由 Maven 打进 JAR 的 `BOOT-INF/classes/static`，运行时不需 Node。

### 6.2 发布到目标机（增量升级）

`deploy/deploy-guide-2.sh` 是完整范例，流程：

1. 把 `app.jar` + `deploy/Dockerfile` + `deploy/refresh-framework.sh` 上传到目标机 `/tmp/mossdoom-framework-bundle/`；
2. 执行 `sudo bash refresh-framework.sh`：重建镜像 `mossdoom/platform:0.1.0` → 读 `current/.env` 更新 `APP_IMAGE=`（锁新镜像 digest）→ `cd current && docker compose up -d app`；
3. 轮询 `web` 容器内 `wget http://app:8080/actuator/health` 直到 `{"status":"UP"}`。

首次全新部署用 `install-framework.sh`（会先建目录、备份、插 app-service、生成密码、建镜像、切 current）；后续功能增量用 `refresh-framework.sh`。

### 6.3 数据库迁移

Flyway 在应用启动时自动执行，无需手工跑 SQL：
- 采集库 `moss_ingestion`：`db/ingestion/` V1~V9（V1 控制面 / V2 采集配置 / V3 endpoint / V4 签名查询 / V5 pin / V6 快照 / V7 gateway / V8 持久化任务 / V9 平台指南）
- 业务库 `moss_business`：`db/business/` V1（通用投影）

验证迁移：`SELECT version, success FROM flyway_schema_history ORDER BY installed_rank;`（注意 `version` 是 varchar，比较须 `version='9'`）。

## 7. 从零部署到新服务器（完整步骤）

```bash
# 1) 准备目录与凭据
sudo mkdir -p /etc/mossdoom/secrets /etc/mossdoom/tls /srv/mossdoom
# 2) 复制一份 releases 快照作为 current 底稿（含 compose.yaml/bootstrap.sh/postgres-init.sh/nginx.conf/prometheus.yml/alerts.yml/index.html/install-*.sh/backup.sh/smoke.py）
sudo rsync -a <某服务器>/opt/mossdoom/releases/<active>/ /opt/mossdoom/releases/<new>/
sudo ln -sfn /opt/mossdoom/releases/<new> /opt/mossdoom/current
# 3) 生成/迁移凭据（见 §4；若从旧机迁移，直接复制 secrets 与 tls 目录，注意 s3.json 里的对象存储身份与数据一致）
# 4) 启动基础设施
cd /opt/mossdoom/current && sudo bash bootstrap.sh
# 5) 构建并部署应用镜像（见 §6.2）
# 6) 验收
python3 smoke.py && sudo bash backup.sh
# 7) 跑端到端（合成数据，不碰真实平台）
python3 deploy/verify-framework.py <报告目录>   # 从代码仓库 deploy/ 取
```

## 8. 跨服务器迁移（数据 + 配置）

1. **停应用**：`cd /opt/mossdoom/current && sudo docker compose stop app`
2. **备份数据库**（在旧机）：
   ```bash
   sudo docker exec mossdoom-test-postgres-1 pg_dump -U moss_admin -Fc moss_ingestion > ingestion.dump
   sudo docker exec mossdoom-test-postgres-1 pg_dump -U moss_admin -Fc moss_business > business.dump
   ```
3. **备份对象存储**：整目录拷贝 `/srv/mossdoom/objectstore/`（SeaweedFS filer 数据）。
4. **迁移凭据**：复制 `/etc/mossdoom/secrets/` 与 `/etc/mossdoom/tls/`（新机 hostname/IP 变了则需重签 TLS，见 bootstrap.sh 的 openssl 段）。
5. **新机恢复**：按 §7 起基础环境后
   ```bash
   sudo docker exec -i mossdoom-test-postgres-1 pg_restore -U moss_admin -d moss_ingestion --clean < ingestion.dump
   sudo docker exec -i mossdoom-test-postgres-1 pg_restore -U moss_admin -d moss_business --clean < business.dump
   ```
6. 恢复对象存储目录到 `/srv/mossdoom/objectstore/`，核对 `connector-targets.json` 与新环境主机是否一致，再 `docker compose up -d`。

## 9. 回滚

```bash
cd /opt/mossdoom/current
OLD=$(cat previous-release)                 # 上一版本路径
sudo docker compose down
sudo ln -sfn "$OLD" /opt/mossdoom/current
cd /opt/mossdoom/current && sudo docker compose up -d
```
注意 Flyway 只前滚不自动回滚；涉及 schema 回退需手工对采集/业务库执行反向 SQL 或从备份恢复。

## 10. 验证边界

- `deploy/verify-framework.py`（管理权限/幂等/异步/隔离/回读/分页）与 `deploy/verify-guide.py`（平台指南）只创建标注「框架验收」的合成数据，**不调用真实业务平台**。
- 不承诺亿级容量、生产高可用、生产迁移完整性；当前测试证书为自签名，生产换可信证书。
- 只读红线：系统对第三方平台/微服务只读，无写接口、无自动全量采集；写操作须管理员显式授权。

## 11. 组件许可证与费用

本项目自部署的全部组件（Java 21 Temurin / Spring Boot / React / PostgreSQL / SeaweedFS / Nginx 开源版 / Prometheus / Docker Engine）均为免费开源、可商用。易踩的「同名商业版」坑（Docker Desktop、Nginx Plus、Oracle JDK）本项目均不使用。详见 `组件许可证与费用清单.md`。

# MOSSDOOM 经营系统 · 架构与 UI 评审（2026-11-12）

评审对象：`E:\codex\project\MOSSDOOM经营系统`（Java 21 / Spring Boot 3.5.16；React 19 / Vite 8）
规模：后端 30 类 2125 行；前端 1179 行（12 个源文件）；Flyway ingestion V1–V10 + business V1。

---

## 一、结论（一句话）

能跑通，但**扩展靠改 Java、页面靠堆 JSX、口径埋在手写 SQL 里**——这不是代码质量问题，是三处结构性缺失：

1. 采集/调度**没有元数据层**（配置在代码里，不在库里）；
2. 经营口径**没有定义的载体**（SQL 就是口径，改口径=改代码）；
3. 前端**没有设计系统和组件层**（所以"丑"且越加越乱）。

---

## 二、逐层诊断（带证据）

### 2.1 采集层：新增一个源 = 改 3 个 Java 文件 + 重新部署

| 证据 | 问题 |
|---|---|
| `CollectionConfiguration.java:44` `if(endpoint.equals("wms.sku-stock"))` | 端点分支写死 |
| `:47` 三元表达式里挂 10 个 + 8 个参数白名单 | 参数白名单是字面量 |
| `:58` 认证种类按 `endpoint.startsWith("gateway.")` 推 | 认证策略写死 |
| `CollectionJobs.java:34` 时间窗口只对 `xinwuyun.produce-orders` 开 | 能力差异写死 |
| `GatewayLogin.java:32` 只认 `gateway.` 前缀 + test 环境 | 同上 |

**后果**：接领星/吉客云/观远，都要动源码；每加一个源就多一条 if 分支；测试机与生产行为无法配置化。

**目标形态**：`collection_endpoint` 表扩成连接器元数据（参数白名单、认证 kinds、分页策略、响应抽取 JSONPath、增量水位字段、并发度、超时），代码里只剩**一个通用执行器**。这样"接一个新平台"= 插一行配置 + 一次 probe 校验。

### 2.2 调度层：单机假设，不可观测

- `@Scheduled(2s)` 排期 + `@Scheduled(1s)` 执行；租约 180s + fence 防并发（这部分是对的）。
- 但：无优先级、无按源并发度、无手动限速、无单次运行时间线；`CircuitBreaker`/`ResponseCache` 是**进程内状态**，多实例部署即失效。
- 失败语义只有 `WAITING_AUTH/WAITING_SOURCE/RETRY/FAILED` 四档，运维看不出"卡在哪一页、哪一步"。

**目标形态**：调度参数入表（优先级/并发/退避/限速）；每次执行落 `collection_job_step`（取页→鉴权→解析→入库 分步耗时）；熔断状态可在内存/Redis 间切换，默认内存、多实例时切 Redis。

### 2.3 服务层：Controller 兼做 SQL、口径、格式化

- `BusinessInsightController.java` 465 行：`@GetMapping` + `queryForList` 大段 SQL + Java 侧聚合 + 字段格式化全在一类里。
- 口径埋在 SQL：`DISTINCT ON (payload->>'apply_no') ... ORDER BY occurred_at DESC`（"每单取最新"这个业务规则），前端换个视角就得改后端。

**目标形态**：`controller`（协议）/ `service`（口径编排）/ `repository`（SQL）；口径抽成**指标注册表**：`metric(id, name, source_dataset, grain, unit, sql_template, definition, owner)`，接口统一 `/api/metrics/{id}?dims=&from=&to=`。前端只认 metric id，不认 SQL。

### 2.4 数据层：全靠 jsonb 现场解析

- `standard_event_projection` 只有 `dataset_id/entity_key/payload/occurred_at`，没有维度表、没有按 dataset 的索引、没有增量水位。
- 现在 220 条没事；到万级，"每页都 DISTINCT ON 全表"必崩。

**目标形态（P2）**：ODS(jsonb 保留) → DWD 维度建模（`dim_spu/dim_sku/dim_shop/dim_factory` + `fact_production/fact_inventory_snapshot/fact_sales`）→ 指标层；至少先补 `(dataset_id, occurred_at)` 组合索引 + 物化视图。

### 2.5 前端：没有设计系统，所以"丑"且不可维护

- `style.css` 是**压缩成 5 行**的单文件（不可读、不可改）；
- `main.tsx` 158 行塞了 nav + 路由 + Login + Table + Modal + Field + Json + Pager 7 个通用件；
- `insight.tsx` / `biz.tsx` / `grid.tsx` 各自重复 KPI、卡片、空态；
- 无路由库（手写 location.hash）、无状态管理、无组件库、无骨架屏、无错误边界、无设计 token（颜色/间距/字号散落各处）。
- 结果：视觉不统一（有的卡有标题栏、有的没有；间距 12/14/16 混用），加一个页面就要复制一棵 JSX。

**目标形态**：
1. **设计 token**（CSS 变量：色板/间距 4-8 阶梯/字号 5 档/圆角/阴影/动效）；
2. **原子组件层** `ui/`：Button / Card / StatCard / Table / Badge / Field / Modal / Tabs / Empty / Skeleton / Toast；
3. **页面 = 组件 + 数据**，页面文件不再出现 HTML 结构细节；
4. 路由表驱动 + 懒加载；错误边界 + 骨架屏统一。

### 2.6 工程化缺口

- 无 CI（构建/单测/部署全靠人肉脚本）；无 lint/format 配置；无 OpenAPI 契约；无 e2e（只有 python 断言脚本）；多环境写死 test。

### P0 · 视觉与组件层（1–2 天，立刻见效，不动后端）

- [ ] 建 `frontend/src/ui/` 原子组件 + `tokens.css`；
- [ ] 重做侧边栏 / 页头 / 卡片 / KPI / 表格 / 空态 / 骨架屏视觉；

**验收**：总览/生产/库存/SKU 四页视觉一致；页面文件不出现裸 `<table>`/`<div className="card">`。

### P1 · 解耦（3–5 天）

- [ ] `collection_endpoint` 扩成连接器元数据表 + 通用执行器（消灭 5 处 if）；
- [ ] `metric` 指标注册表 + `/api/metrics/{id}`，`BusinessInsightController` 拆 service/repository；
- [ ] 调度参数入表（优先级/并发/退避/限速）+ `collection_job_step` 过程留痕。

**验收**：新增一个同构平台源 = 插配置 + probe，不改 Java；新增一个指标 = 插一行 metric。

### P2 · 可扩展与多实例（1–2 周）

- [ ] 页面注册表（nav/route/cards 由配置生成，前端插件化）；
- [ ] 熔断/缓存可切 Redis；多实例安全；
- [ ] DWD 维度建模 + 物化视图 + 索引；
- [ ] CI（build+test+deploy）+ OpenAPI + 前端 e2e。

## 四、建议的启动顺序

1. **P0 先做**：用户感知最强（页面），风险最低（不碰后端），一天能看见；
2. P1 的**连接器元数据**优先于指标注册表（它直接决定"能不能接领星/吉客云"）；
3. P2 的维度建模等销量口径确认后再做（口径未定先建模会返工）。

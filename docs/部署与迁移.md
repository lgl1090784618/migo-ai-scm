# 部署与迁移

## 测试部署现状

机器为用户指定的 `192.168.10.154`，Ubuntu24.04，4核8G。Docker Compose 项目固定为 mossdoom-test，当前发布目录 `/opt/mossdoom/releases/20261111-framework-04`，稳定入口 `/opt/mossdoom/current`。持久数据在 `/srv/mossdoom`，凭据和 TLS 在 `/etc/mossdoom`。未在 Windows 本机部署另一个对外监控平台。

应用镜像使用 Java21，非 root 用户、只读根文件系统、临时目录限额，内存上限1536MiB。PostgreSQL、S3测试存储、Prometheus、node-exporter沿用现有基础环境。只公开 HTTPS8443；应用8080和数据库5432只在 Compose 网络内，S3宿主端口仅绑定localhost。应用管理接口和采集接口统一经 Nginx 进入，Prometheus 指标端点只在内部网络开放。

启动过程先完成双库 Flyway 迁移，然后启动 worker 与 Web。现有 infra_verification 验证数据保留，没有重建或清空原数据库。应用分离使用采集库和业务库账号；首版账号仍有本库迁移权限，生产需拆出专用迁移角色。

## 安装与更新

1. 本地先构建前端，再把静态资源打入 JAR；执行单元测试。依赖和构建目录使用 E 盘任务 work/framework 下的路径。
2. 准备部署包：Dockerfile、app.jar、app-service.yaml、nginx.conf、backup.sh、install-framework.sh。校验 JAR SHA-256后上传指定服务器。
3. 首次追加框架时，以 sudo 执行 install-framework.sh。该脚本仅支持已部署的基础环境；先备份，复制旧发布到新发布，追加应用服务及 Prometheus 抓取，生成独立管理密码并挂载已有双库/S3凭据。
4. 构建锁定 Java 基础摘要的应用镜像，将完整镜像ID写入服务器发布 .env。先启动应用并通过内部健康检查，再切换 Nginx、Prometheus及 current 链接。
5. 开发阶段的 refresh-framework.sh 只用于本次测试发布目录内替换 JAR并重建应用镜像；它不应作为生产发布流程。生产每次使用新的不可覆盖发布目录和镜像摘要。
6. 执行 verify-framework.py 指向 E 盘日志目录；该脚本需本机 SSH密钥、Python3及指定测试机访问权限。无论脚本成功与否，验收数据均有明确名称；失败中断后需检查未吊销的验收令牌和未暂停的验收连接。脚本不会读取或调用真实平台凭据。

## 备份、恢复与回滚

现有备份定时器每日北京时间02:30触发。新 backup.sh 先停止应用，阻止接收和 worker 写入，再分别转储采集与业务数据库，然后停止对象存储复制数据；最后启动对象存储与应用。这是测试环境短暂停机备份，通常会出现短时页面不可用；不能当作生产零停机方案。备份失败的 trap 会尝试重启服务，执行后仍必须检查健康状态。

备份包含数据库、对象数据、镜像锁定、配置以及受控凭据/TLS归档，目录权限700。它属于敏感运维备份，不可直接作为普通交付包发送。没有自动清理策略，需监控50GB磁盘空间，异机备份与保留期另行落实。

restore-check.sh 在全新的隔离网络与数据目录恢复，不覆盖在线数据，不发布测试端口。现已完成包含框架表的双库及对象存储恢复；该脚本基础断言验证 infra 标记与S3样本可读，仍需结合框架批次、投影及对象hash对照，才能作为生产恢复验收。

回退到基础环境时，先停止应用，再用 previous-release 指向的旧目录重建 web/prometheus，并切回 current；新增数据库表保留，不执行反向 DROP。对后续版本，若迁移有不兼容变化，仅回退镜像不能恢复数据，应按备份恢复到独立实例验证后切换。

## 生产迁移方案

当前测试数据不自动带入生产。先区分配置迁移和业务数据迁移；真实平台签名、授权、增量边界、实体键、删除语义及业务规则必须逐一确认。test硬编码、单租户账号及默认平台目录不可直接作为正式多租户系统上线。

生产准备独立数据库、对象存储、密钥系统、域名可信证书、镜像仓库、备份存储和监控通知。按实际吞吐决定接收服务和 worker 数量，先对单实例与多worker做压测及租约恢复测试；应用目前可通过队列行锁协调worker，但尚未完成分布式会话、共享限流和多实例部署验收。

迁移顺序：创建新基础环境→专用角色执行版本迁移→部署应用并验证内部依赖→迁入不含令牌的已确认配置→重新签发正式凭据→只读接入一个平台小范围试运行→核对原文、批次及业务投影→再扩平台/站点。迁移窗口暂停外部生产方提交、排空任务，确认双库与对象清单一致后切换入口；失败时回旧入口并以原幂等键重试。

接入亿级数据前补齐月分区维护、元数据归档、去重表容量策略、分片与分析存储、恢复时间和恢复点目标，并根据容量实测调整架构。当前4核8G机器只承担框架验证，不作为亿级承载承诺。
